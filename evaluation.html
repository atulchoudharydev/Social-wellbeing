1. Evaluation methods

The prototype was evaluated several times while it was being built, using a mix of expert review, automated testing and design feedback. Each method looks for a different kind of problem.

2. Design iterations

The interface went through three main versions. Each was based on Option C (the guided hybrid) from the design options; what changed was the visual design and the details of each component.

  1. v1First build

    Working prototype of Option C

    All six required pages built with the accordion directory, calendar, booking wizard and mobile menu. Teal and orange palette with emoji icons and a gradient hero.

    Feedback: the interface felt cluttered and "tacky". Emoji icons looked different on each device and the gradient and colours felt dated.

  2. v2Redesign

    Calmer, editorial redesign

    New type pairing (Source Serif 4 and Public Sans), a consistent line-icon set, static HTML header and footer, a "Display" menu for text size and contrast, and a design critique to remove generic patterns.

    Feedback: cleaner, but now "boring and plain". It needed real imagery and more colour to feel welcoming and engaging.

  3. v3Final

    Warm, photographic and accessible

    Real photography of diverse residents, a brighter teal, coral and sunshine palette, an accessible hero image slider, a stories carousel and topic photo cards. An automated accessibility audit was then run and every issue fixed.

Interactive states were also tested: form error messages, the open mobile menu and Display menu, the article pop-up and high-contrast mode. Automated tools find only part of all accessibility problems, so keyboard-only and zoom testing were also done by hand. Testing with screen-reader users would be the next step.

Accessibility features

  • "Skip to main content" link and clear heading structure on every page
  • Highly visible yellow and black keyboard focus indicator
  • Display menu for larger text and high contrast, remembered between visits
  • Forms with visible labels, hints, an error summary linking to each problem and inline error messages
  • Accordion, carousel, dialog and step-by-step form follow WAI-ARIA Authoring Practices
  • Movement respects the "reduce motion" setting; every photo has descriptive alt text
  • Buttons and links at least 44 by 44 pixels for easier tapping

6. Usability test plan

The next round of evaluation is task-based testing with 5 people who reflect the Hub's users: an older adult, a parent, a younger adult, someone with low confidence online, and someone who uses a screen reader or magnification. Each person tries the tasks below while thinking aloud.

  1. Find support for anxiety

    Success: reaches the Mental health section of the service directory and names a service.

  2. Book 2 places on a health walk

    Success: completes the booking and sees a reference number.

  3. Find out when the Hub is open on Saturday

    Success: finds the opening times on the Contact page or homepage.

  4. Make the text bigger

    Success: uses the Display menu to choose a larger text size.

  5. Read a resident's success story

    Success: opens a story from the homepage carousel or the News page.

What will be measured

  • Task completion rate and time on task
  • Errors and moments of hesitation
  • System Usability Scale (SUS) score after the session
  • Comments, recorded and grouped into themes

Problems found will be rated for severity and fixed in the same way as the findings above.
